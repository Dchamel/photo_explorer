# План по конкурентности (этап 4.6)

> Документ ведёт **Джарвис** (архитектор). Цель — методично, без спешки,
> ввести многопоточность в загрузку изображений. Прошлый опыт (этап 4.3)
> показал: гонки чинятся долго, если лезть в потоки без видимости и плана.
> Поэтому эксперименты идут фазами, каждая — отдельный под-этап с тестом
> и возможностью отката на тег `v0.2.0`.

---

## 1. Зачем это (симптом)

При открытии проекта и листании «размытая миниатюра висит ~10 секунд,
потом прогружается чёткое». Причина — **один воркер-поток делает ВСЁ по
очереди**, и три нагрузки конкурируют за него:

1. **Батчи миниатюр галереи** (4.4b) — отдельный `thread::spawn`, строит
   все 10653 миниатюры порциями (тяжёлый CPU).
2. **Чёткое фото текущего кадра** (`LoadTask::Photo`) — декод полного
   изображения через `load_full_image`.
3. **Предзагрузка 3 соседей** (`LoadTask::Preload`) — тоже через воркер.

Когда пользователь открывает фото, пока батчи ещё идут, очередь воркера
забита, и чёткое ждёт → «висит размытое». `drain_to_last` берёт последнюю
`Photo`-задачу, но НЕ прерывает уже идущий декод соседа/батча.

---

## 2. Принцип решения

**Приоритет текущего кадра над всем фоном.** Чёткое фото, которое
пользователь смотрит ПРЯМО СЕЙЧАС, декодируется вперёд предзагрузки и
батчей. Остальное — по остаточному принципу.

В Rust для CPU-декода + файлового I/O идеальны **потоки + rayon**
(не процессы, не async): компилятор через типы `Send`/`Sync` не даёт
сделать гонку данных — «бесстрашный параллелизм».

---

## 3. Фазы (каждая — отдельный под-этап, тест, при проблеме откат на v0.2.0)

### Фаза 0 — подробные логи (ВИДИМОСТЬ) — 4.6a ✅ ВЫПОЛНЕНА

Прежде чем трогать потоки, сделать гонки ВИДИМЫМИ в логе. Добавить:

- **Каждая задача воркера:** `task_id` (счётчик), тип (Photo/Preload),
  индекс, поколение, время старта и конца декода (мс).
- **Каждая запись в `viewer-image`:** источник (миниатюра / UI-кэш /
  RGBA-кэш / воркер), индекс задачи, текущий `viewer-index`, совпали ли.
- **Очередь:** сколько задач в канале на момент приёма (глубина).
- **Батчи миниатюр:** старт/конец батча, номер, размер.

Формат — единообразный префикс, чтобы грепать: `[CONC] ...`.
Критерий фазы: по логу можно восстановить точную последовательность
событий при любом глюке, без догадок.

### Фаза 1 — приоритет на ОДНОМ потоке (минимальный риск) — 4.6b ✅ ВЫПОЛНЕНА

> **Подтверждено логом `[CONC]` (сессия 16:35:26–16:36:03, random):**
> причина «размытой 10 сек» — тяжёлый `Preload` соседа встаёт ПЕРЕД
> `Photo` текущего кадра в одной FIFO-очереди. Примеры:
> - idx=411: миниатюра показана в `52.030`, но воркер занят Preload
>   `2aea57…png` (downscale 1536×2736, декод **2999 мс**); чёткое
>   idx=411 декодировано только в `54.998` → ~3 с «висит размытое».
> - idx=9870: Preload `0e8d09…jpeg` (downscale 3840×2160) занял
>   **5491 мс**; Photo ждал всё это время.
> - `drain_to_last` берёт последнюю Photo, но НЕ прерывает уже идущий
>   декод Preload — поэтому приоритет нужен на уровне ДИСЦИПЛИНЫ очереди.
> Инвариант «кадр = viewer-index» в логе НЕ нарушен (рассинхрона нет).

НЕ добавляем новых потоков (нет новых гонок — поток один, инвариант
«кадр = viewer-index» уже есть). Меняем дисциплину очереди:

- Разделить канал на ДВА: `priority_rx` (только `Photo` — текущий кадр)
  и `bg_rx` (`Preload`). Воркер в цикле: сначала опустошает `priority`
  (с `drain_to_last`), и ТОЛЬКО если там пусто — берёт одну `bg`-задачу.
- Так текущее чёткое всегда декодируется раньше соседей.
- Батчи миниатюр галереи пока не трогаем (отдельный поток).

Критерий: «размытая висит 10 сек» уходит при обычном листании (чёткое
приходит первым). Тест на логах: `Photo` всегда декодируется до `Preload`.

> **ПРИНЯТА (лог 18:02:39–18:04:05):** очередь больше не блокирует
> кадр — Photo декодируется сразу, соседи не мешают. Оставшийся тормоз
> — скорость декода ОДНОГО тяжёлого файла (PNG 5760×6480: downscale
> 15.9 с на одном ядре i5-1235U, очередь пуста) → это Фаза 2.

### Фаза 2 — многопоточность по одному потоку — 4.6c (если фазы 1 мало) — СЛЕДУЮЩАЯ

Вводим параллелизм ОСТОРОЖНО, по одному потоку, тест после каждого.
По решению заказчика (приёмка Фазы 1): главный тормоз теперь — декод
ОДНОГО тяжёлого файла на одном ядре, поэтому порядок шагов изменён:

- **Шаг 2a (главный):** многопоточный ДЕКОД/resize тяжёлых файлов —
  через `rayon` (уже подключён) по всем ядрам. Настройка-галка
  «Ультра-скорость» в панели ⚙, по умолчанию ВЫКЛЮЧЕНА — все ядра
  греют ноут и жгут батарею (i5-1235U — 15-ваттный чип), экономичный
  режим остаётся поведением по умолчанию. Заодно — подписи ко всем
  блокам настроек (понятно пользователю, что каждая делает).
- **Шаг 2b (если нужно):** батчи миниатюр галереи через `rayon`
  (`par_iter` по чанку) и/или отдельный поток-декодер для `Preload`.
  Два декода параллельно — больше RAM (каждый RGBA ~26 МБ). Вводим
  только если 2a не хватило.

Критерий: тяжёлый файл (5760×6480) декодируется кратно быстрее при
включённой галке; без галки поведение не меняется; память под
контролем (LRU 40).

## 4. Правила безопасности экспериментов

- После КАЖДОЙ фазы — `cargo fmt/clippy/test` + ручной тест заказчиком,
  СТОП и приёмка.
- Инвариант «на экране кадр = viewer-index» (4.4c-5/6) НЕ ломаем — любая
  новая запись в слой сверяет индекс.
- При регрессе — откат `git checkout v0.2.0`, разбор по логам фазы 0.
- Число параллельных декодов ограничено (RAM): не больше 2-3 крупных
  одновременно.

---

## 5. Почему не процессы и не async

- **Процессы** — для изоляции сбоев/безопасности; у нас одна программа,
  общая память нужна (кэши) — процессы дали бы накладные расходы на IPC.
- **async/корутины** — для тысяч одновременных I/O-ожиданий (сеть); у нас
  десяток тяжёлых CPU-задач (декод) — тут рулят потоки + пул (rayon).
- **Потоки + rayon** — штатный инструмент Rust для CPU-параллелизма,
  проверяется компилятором (Send/Sync) — минимум риска гонок данных.
