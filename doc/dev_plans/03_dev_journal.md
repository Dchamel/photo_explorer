## Этап 1. Фундамент проекта (Cargo + CI)

### Что сделали
- Создали `Cargo.toml` — манифест проекта (имя, версия, зависимости).
- Создали `src/main.rs` — точку входа (функция `main`, с которой стартует программа).
- Настроили `.github/workflows/ci.yml` — автопроверку кода на GitHub.

### Зачем
Чтобы был работающий каркас, который собирается и запускается, и чтобы GitHub
автоматически проверял качество кода при каждом пуше.

### Почему именно так

**Про `Cargo.toml`.** В Rust это аналог `package.json` (Node) или `requirements.txt` (Python).
Cargo — инструмент «всё в одном»: собирает проект, качает зависимости, запускает тесты.

**Про `main.rs`.** Файл `src/main.rs` — особенный: Rust ищет в нём функцию `fn main()`
как точку старта программы. Пока это была заглушка с `println!` (печать текста).

**Про CI (`ci.yml`).** Это НЕ «CI/CD для сайта» (деплой на сервер нам не нужен — приложение десктопное).
Это просто робот на GitHub, который при каждом пуше запускает 4 проверки:
| Команда | Что проверяет |
|---------|---------------|
| `cargo fmt --check` | код отформатирован по единому стандарту |
| `cargo clippy` | линтер: нет подозрительного кода и плохих практик |
| `cargo build` | проект собирается без ошибок |
| `cargo test` | все тесты проходят |

Если что-то сломано — GitHub покажет красный крестик. Это наша «страховка».

## Этап 2. Ядро и сканер папок

### Что сделали
- Создали модуль `src/core/` — «ядро» приложения:
  - `models.rs` — доменные модели `Photo` и `ScanMode`;
  - `ports.rs` — трейт `PhotoScanner` (порт) и тип ошибок `ScanError`.
- Создали модуль `src/scanner/` — адаптер `FileSystemScanner` (реализация сканера).
- Создали `src/lib.rs` — библиотечный корень (чтобы код был доступен в тестах).
- Написали 7 автотестов в `tests/scanner_tests.rs`.

### Зачем
Это первый «рабочий орган» приложения — поиск фотографий в папках.
Пользователь выбирает папку, а сканер находит в ней все изображения.

### Почему именно так — ключевые концепции Rust и архитектуры

#### 1. Что такое «модуль» в Rust
Модуль — это способ сгруппировать код. В Rust **папка = модуль**.
Папка `src/core/` с файлом `mod.rs` — это модуль `core`. Внутри него подмодули
`models` и `ports` (отдельные файлы). Так код не превращается в кашу.

#### 2. Доменные модели (`models.rs`) — `struct` и `enum`

**`struct Photo`** — это «структура», набор полей (как карточка объекта):
```rust
pub struct Photo {
    pub path: PathBuf,      // путь к файлу
    pub file_name: String,  // имя файла
    pub size_bytes: u64,    // размер в байтах
}
```
`pub` означает «публичный» — поле видно за пределами модуля.

**`enum ScanMode`** — это «перечисление», выбор одного из вариантов:
```rust
pub enum ScanMode {
    AllDrives,                   // все диски
    SingleFolder(PathBuf),       // одна папка
    FolderRecursive(PathBuf),    // папка + подпапки
}
```
`enum` в Rust мощнее, чем в других языках: вариант может нести данные
(например, `SingleFolder` хранит путь к папке). Это паттерн **Strategy** —
поведение сканера меняется в зависимости от выбранного варианта.

#### 3. Порт — трейт (`ports.rs`)

**Трейт** — это «контракт», описание того, что объект умеет делать (как интерфейс):
```rust
pub trait PhotoScanner {
    fn scan(&self, mode: &ScanMode) -> Result<Vec<Photo>, ScanError>;
}
```
Здесь написано: «любой сканер обязан иметь метод `scan`, который принимает режим
и возвращает либо список фото, либо ошибку». Но КАК именно сканировать — трейт не говорит.
Это и есть **порт** в Hexagonal-архитектуре.

**`Result<Vec<Photo>, ScanError>`** — так Rust обрабатывает ошибки без исключений:
результат это ЛИБО успех (`Ok` со списком фото), ЛИБО ошибка (`Err`). Программа обязана
обработать оба случая — поэтому Rust так надёжен.

#### 4. Адаптер — реализация (`scanner/mod.rs`)

**`FileSystemScanner`** — конкретная реализация трейта поверх реальной файловой системы:
```rust
impl PhotoScanner for FileSystemScanner {
    fn scan(&self, mode: &ScanMode) -> Result<Vec<Photo>, ScanError> {
        // ... реальный обход папок через библиотеку walkdir
    }
}
```
`impl ... for ...` означает «реализуем контракт `PhotoScanner` для структуры `FileSystemScanner`».

**Почему порт и адаптер разделены (главная мысль):**
Ядро знает только про трейт `PhotoScanner`, но не про `walkdir` и не про Windows.
Если завтра захотим искать фото в облаке или в базе данных — напишем новый адаптер,
а ядро и интерфейс не изменятся ни на строчку. Это принцип **D** из SOLID
(Dependency Inversion — зависим от абстракций, а не от деталей).

#### 5. Фильтрация форматов
Сканер берёт только изображения с расширениями `jpg, jpeg, png, gif, bmp, webp`
(сравнение без учёта регистра, т.е. `.JPG` и `.jpg` — одно и то же).

#### 6. Зачем `lib.rs`
В Rust бинарник (`main.rs`) и тесты (`tests/`) — это разные «ящики» (crate).
Чтобы тесты видели наш код, мы вынесли его в библиотеку `lib.rs`.
Теперь и программа, и тесты пользуются одним и тем же кодом — принцип **DRY** (не повторяйся).

### Про тесты (`tests/scanner_tests.rs`)
Написали 7 проверок: находит ли сканер нужные форматы, игнорирует ли лишние,
работает ли рекурсия, правильно ли возвращает ошибки на несуществующий путь и т.д.
Тесты создают временные папки с фейковыми файлами и проверяют поведение.

**Важный урок:** первый запуск тестов упал по двум причинам —
1) тесты в Rust бегут **параллельно**, и они мешали друг другу через общую папку
(исправили уникальными именами);
2) тест скана всех дисков длился 60+ секунд (пометили `#[ignore]`).
Это нормальная часть разработки — тесты для того и нужны, чтобы ловить такое.

### Решение по итогам приёмки (заказчик)
Режим `AllDrives` (скан всех дисков) пока **отключается** (закомментирован в коде
с пометкой на будущее). Работаем только с режимами `SingleFolder` и `FolderRecursive`.
Причина: скан всех дисков медленный и для текущих задач не нужен — принцип **KISS**.

## Этап 2 (продолжение). Модуль thumbnails — миниатюры

### Что сделали
- В ядро добавили модель `Thumbnail` и порт-трейт `ThumbnailProvider`.
- Создали адаптер `src/thumbnails/` — `FileSystemThumbnailProvider`.
- Добавили библиотеки `image` (декодирование/изменение размера) и `rayon` (параллелизм).
- Написали 5 автотестов в `tests/thumbnails_tests.rs`.

### Зачем
Сканер находит файлы, но чтобы показать **сетку фото**, нужны маленькие картинки-миниатюры.
Генерировать их из 10-мегапиксельных оригиналов каждый раз заново — медленно.
Поэтому миниатюры **кэшируются** на диске.

### Почему именно так — ключевые концепции

#### 1. Модель `Thumbnail`
```rust
pub struct Thumbnail {
    pub source_path: PathBuf, // связь с исходным фото
    pub width: u32,
    pub height: u32,
    pub data: Vec<u8>,        // пиксели в формате RGBA (4 байта на пиксель)
}
```
`Vec<u8>` — это динамический массив байтов (вектор). В отличие от массива
фиксированной длины, его размер известен только во время работы программы.

#### 2. Порт `ThumbnailProvider`
```rust
pub trait ThumbnailProvider {
    fn thumbnail(&self, photo: &Photo) -> Result<Thumbnail, ThumbnailError>;
    fn thumbnails(&self, photos: &[Photo]) -> Vec<Result<Thumbnail, ThumbnailError>>;
}
```
Два метода: для одного фото и для пакета. Пакетный возвращает **вектор результатов**
(а не `Result` целиком), потому что часть фото может обработаться успешно, а часть — с ошибкой,
и мы не хотим из-за одного битого файла терять все остальные.

#### 3. Кэширование — как это работает
- Путь к файлу кэша = **хеш** абсолютного пути исходника (через `DefaultHasher`).
  Хеш — это «цифровой отпечаток» строки: одинаковые пути дают одинаковые имена кэша,
  но короткие и без спецсимволов.
- Кэш считается **валидным**, если файл кэша существует и его дата изменения (mtime)
  **не старее** даты изменения исходника. Если оригинал поправили — миниатюра перегенерируется.
- Кэш хранится в формате **PNG** (без потерь, быстро читается).

#### 4. Параллелизм через `rayon`
```rust
photos.par_iter().map(|photo| self.thumbnail(photo)).collect()
```
`par_iter` — это «параллельный итератор» из библиотеки `rayon`. Он автоматически
раскидывает работу по ядрам процессора. Если у тебя 8 ядер и 100 фото — обработка
идёт примерно в 8 раз быстрее, чем по одному. Порядок результата сохраняется.

**Почему это безопасно в Rust:** `rayon` гарантирует, что разные потоки не наступят
друг на друга. Это то, за что Rust любят — параллельный код без гонки данных.

#### 5. Изменение размера с сохранением пропорций
```rust
img.resize(max_size, max_size, FilterType::Lanczos3)
```
`resize` вписывает изображение в рамку `max_size × max_size`, **сохраняя пропорции**
(фото 800×600 при max=200 станет 200×150, а не 200×200). `Lanczos3` — качественный
алгоритм ресайза (медленнее, но красивее; для миниатюр это оправдано).

#### 6. Обработка ошибок — почему «ошибка кэша не ломает результат»
При записи в кэш мы пишем `let _ = save_thumbnail_to_cache(...)`.
`let _` означает «результат игнорируем». Логика: если кэш записать не получилось
(нет места на диске, нет прав), миниатюра всё равно отдаётся пользователю —
просто в следующий раз сгенерируется заново. Это мягкая деградация, принцип
«лучше показать без кэша, чем упасть».

### Про тесты
5 проверок: миниатюра меньше оригинала и с правильными пропорциями,
кэш реально создаётся и читается, пакет сохраняет порядок, повреждённый
и несуществующий файлы дают ошибку. Тесты создают **настоящие PNG** через
библиотеку `image` — не моки, а реальная генерация.

## Этап 2 (продолжение). Модуль security — защита доступа

### Что сделали
- В ядро добавили порты `Authenticator` и `SessionLockWatcher`, тип `AuthOutcome` и ошибки `SecurityError`.
- Создали модуль `src/security/`:
  - `pin.rs` — чистая логика хеширования PIN через **Argon2** (полностью тестируемая);
  - `mod.rs` — `SecurityService`: хранит хеш PIN в файле, реализует `Authenticator`;
  - `windows_hello.rs` — Windows Hello (биометрия), только под Windows;
  - `session_lock.rs` — наблюдатель блокировки сессии (заглушка, полная версия на Этап 3).
- Написали 6 юнит-тестов PIN + 5 интеграционных тестов `SecurityService`.

### Зачем
Защита приложения от «случайного человека рядом с ноутбуком»: вход по отпечатку
(Windows Hello) или PIN. При блокировке Windows (Win+L) приложение тоже должно блокироваться.

### Почему именно так — ключевые концепции

#### 1. PIN хранится ТОЛЬКО как хеш (Argon2)
```rust
pub fn hash_pin(pin: &str) -> Result<String, SecurityError> {
    let salt = SaltString::generate(&mut OsRng);   // случайная соль
    Argon2::default().hash_password(pin.as_bytes(), &salt)...
}
```
**Хеш** — это одностороннее преобразование: из PIN легко получить хеш, из хеша PIN — практически невозможно.
Поэтому даже если кто-то украдёт файл с хешем, PIN он не узнает.
**Соль** (`SaltString`) — случайная добавка, чтобы два одинаковых PIN давали разные хеши
(защита от «радужных таблиц»). Argon2 — современный алгоритм, специально медленный
(чтобы пер) — это замедляет перебор.

**Важно:** на диске лежит строка вида `$argon2id$...` (PHC-формат), сама строка `"1234"` там не встречается.
Тест `pin_is_stored_as_hash_not_plaintext` это проверяет.

#### 2. Разделение тестируемого и нетестируемого (главный архитектурный приём)
Windows Hello и блокировка сессии **нельзя автотестировать** в CI: на сервере GitHub
нет сканера отпечатка и нет интерактивной сессии. Поэтому:
- **чистую логику** (хеш/проверка PIN) вынесли в `pin.rs` без зависимости от ОС → покрыли тестами;
- **Windows-специфику** изолировали за `cfg(windows)` и за трейтами → компилируется, но без тестов.

Это тот же принцип Hexagonal: тестируем ядро, адаптеры к ОС проверяем вручную.

#### 3. `cfg(windows)` — условная компиляция
```rust
#[cfg(windows)]
pub mod windows_hello;
```
Атрибут `#[cfg(windows)]` означает «компилировать этот модуль только на Windows».
Аналогично в `Cargo.toml` зависимость `windows` добавлена в секцию
`[target.'cfg(windows)'.dependencies]` — она не тянется на других ОС.
Это делает ядро кроссплатформенным, а Windows-фичиE — опциональными.

#### 4. Windows Hello — какB как это работает
```rust
UserConsentVerifier::RequestVerificationAsync(&HSTRING::new())?
```
Мы! Мы просим ОС: «покажи пользователю запрос биометрии и скажи, подтвердил ли он».
**Приложение не получает сам отпечаток пальца** — это запрещено Windows ради безопасности.
Мы получаем только ответ: `Verified` / `Canceled` / `DeviceNotPresent` и т.д.
Это правильный, безопасный подход.

#### 5. Блокировка по Win+L — почему заглушка сейчас
Полная реализация требует цикла сообщений Win32 (`WTSRegisterSessionNotification` +
`WM_WTSSESSION_CHANGE`) и скрытого окна. Это нетривиально и **проверяется только на реальной машине**
с графической сессией. По принципу KISS мы оставили заглушку с `TODO(Этап 3)` и подключим
полную версию вместе с окном приложения на этапе UI — там её можно будет проверить вручную.

#### 6. `AuthOutcome` вместо bool
```rust
pub enum AuthOutcome { Granted, Denied }
```
Возвращаем не `bool`, а явный enum. Так нельзя перепутать `true`/`false` (что значит «успех»?),
и легко добавить новые состояния (например, `Retriable`) без изменения сигнатур.

### Про тесты
- 6 юнит-тестов в `pin.rs`: верный/неверный PIN, хеш ≠ PIN, разная соль, пустой PIN, битый хеш.
- 5 интеграционных тестов в `security_tests.rs`: set+verify, неверный → Denied, хеш не plaintext,
  verify без set → ошибка, перезапись PIN.
- Windows Hello и блокировку автотестами НЕ покрываем (нет среды в CI) — только компиляция.

### Решение по итогам
Уровень защиты — «от случайного человека» (согласовано с заказчиком). Файлы фото на диске
остаются доступны через проводник; полное шифрование хранилища — в бэклоге.

## Этап 3. Экран блокировки на Slint

### Что сделали
- Добавили библиотеку **Slint** (GUI-фреймворк) и `slint-build` (сборщик `.slint`-разметки).
- Создали `build.rs` — скрипт, который на этапе сборки компилирует `.slint`-файлы в Rust-код.
- Создали `src/ui/views/lock.slint` — разметку экрана блокировки (тёмная тема, синий акцент).
- Создали `src/ui/mod.rs` — `LockController`, связывающий экран с `SecurityService`.
- `main.rs` теперь запускает **настоящее окно** с экраном блокировки.

### Зачем
Впервые у приложения есть интерфейс, который видит пользователь. Первый экран — блокировка:
вход по PIN или отпечатку. Это «ворота» в приложение.

### Почему именно так — ключевые концепции

#### 1. Что такое Slint и `.slint`-файл
Slint — декларативный UI-фреймворк для Rust. Разметка интерфейса пишется в отдельном языке
(похож на QML/CSS) в файлах `.slint`, а логика — на Rust. Это разделение «как выглядит» и
«как работает» — чисто и читаемо. Ты, не зная Rust глубоко, можешь читать `.slint` и понимать вид.

#### 2. `build.rs` — сборочный скрипт
```rust
slint_build::compile("src/ui/views/lock.slint")
```
Это специальный файл, который Cargo запускает **до** компиляции основного кода.
Он превращает `.slint`-разметку в Rust-код (макрос `include_modules!()` потом его подключает).
Без `build.rs` Slint не узнает про наши экраны.

#### 3. `global Theme` — палитра цветов
```slint
export global Theme {
    in-out property <color> background: #1E1E1E;
    in-out property <color> accent: #3B82F6;
    ...
}
```
Все цвета собраны в одном месте (`Theme`). Хочешь поменять акцент с синего на зелёный —
правишь одну строку, и весь интерфейс обновляется. Это принцип **DRY** для дизайна.
`in-out` означает, что свойство доступно для чтения и записи снаружи global.

#### 4. Свойства и колбэки — мост между Slint и Rust
```slint
in-out property <string> pin-text: "";
callback login();
```
- **Свойство** (`property`) — данные, которые текут между UI и Rust (например, текст поля PIN).
- **Колбэк** (`callback`) — сигнал от UI к Rust (например, «нажали Войти»).
В Rust мы подписываемся на колбэк: `ui.on_login(move || { ... проверка PIN ... })`.
Это и есть связка «вида» и «логики».

#### 5. `LockController` — контроллер (паттерн MVC-подобный)
`LockController` держит `SecurityService` и переводит действия UI в вызовы ядра:
- `on_login(pin)` → `verify_pin` → `Granted`/`Denied`;
- `on_create_pin(pin)` → `set_pin`;
- `on_biometric()` → `authenticate_biometric` (Windows Hello).
Ядро (`security`) ничего не знает про Slint — контроллер адаптирует его к UI.
3. Это тот же принцип Ports & Adapters: UI — отдельный слой, ядро не загрязнено.

#### 6. `ui.as_weak()` — зачем «слабая» ссылка
В колбэках мы используем `ui.as_weak()`, а не `ui` напрямую. Причина: колбэк может
сработать **после** уничтожения окна (пользователь закрыл). Слабая ссылка безопасна:
если окна уже нет — ничего не упадёт. Это типичная для Rust забота о времени жизни.

#### 7. Режим «Создать PIN» / «Войти»
Если PIN ещё не задан (`has_pin() == false`), экран сразу показывает режим создания.
После создания — переключается в режим входа. Один экран, два состояния — через свойство
`is-creating-pin`. Это проще, чем два отдельных экрана (KISS).

### Про сборку
Slint тянет много зависимостей (рендеринг, шрифты, окно) — первая сборка долгая (~30 сек),
последующие быстрые. CI на windows-latest собирает без проблем: Slint использует
software-рендеринг по умолчанию, системные библиотеки не нужны.

### Что увидит заказчик при `cargo run`
Впервые откроется **настоящее окно**: тёмный фон, по центру замок 🔒, заголовок «Photo Explorer»,
поле для PIN, синяя кнопка «Создать PIN» (при первом запуске) и кнопка «Отпечаток пальца».
Это момент, когда проект из «кода в терминале» превращается в приложение.

## Почему нет прямого доступа к сканеру отпечатка

Заказчик спросил: «Почему мы не можем подключаться к сканеру напрямую? Это же железо ноутбука,
не собственность Windows?» — отличный вопрос. Краткий ответ и подробный.

### Кратко
Физически сканер твой. Но доступ к нему **намеренно закрыт на уровне ОС и железа** —
ради твоей же безопасности. Мы получаем только ответ «владелец: да/нет», сам отпечаток недоступен.

### Подробно
1. **Отпечаток хранится в защищённом чипе (TPM), не в файле.** При настройке Windows Hello
   отпечаток превращается в математический шаблон и шифруется в аппаратном модуле (TPM /
   Secure Enclave). Даже Windows не может его «прочитать» как картинку — только спросить чип
   «это владелец?».

2. **Если бы приложения читали сканер напрямую** — любая программа (включая вирус) могла бы
   снять отпечаток и украсть его. А отпечаток, в отличие от пароля, **нельзя сменить**.
   Поэтому Microsoft, Apple и Android — все одинаково закрыли прямой доступ. Это индустриальный
   стандарт безопасности, не жадность Windows.

3. **Что нам доступно** — API `UserConsentVerifier`: просим «подтверди владельца», ОС сама
   рисует запрос, сама читает палец в защищённой среде, возвращает нам только `да`/`нет`.
   Это максимум, что можно и нужно.

### Вывод для проекта
Системное окно Windows Hello убрать нельзя (его рисует ОС). Но мы убрали **лишние клики
с нашей стороны**: автозапрос при старте + вывод окна на передний план. Формула
«Запустил → Приложил → Зашёл» достижима — системный запрос просто часть шага «Приложил».
Это честный максимум в рамках безопасности ОС.

## Этап 3 (продолжение). Блокировка v3 — встроенная клавиатура и исправление биометрии

### Что сделали
- **Всё в одном окне:** убрали отдельное окно клавиатуры. Точки PIN и сама клавиатура —
  на основном экране `LockScreen`.
- **Клавиатура встроенная:** кнопка «Войти по PIN» показывает клавиатуру прямо в окне
  (окно раздвигается по высоте через `preferred-height: show-keyboard ? 560px : 320px`).
- **Автовход:** 4 верные цифры = автоматический вход (без кнопки «ОК»). Неверный PIN —
  красное сообщение, точки сбрасываются.
- **Исправлен баг биометрии:** убран вызов из фонового потока; теперь автозапрос через
  `slint::Timer::single_shot` из UI-потока.

### Зачем
По отзыву заказчика: отдельное окно клавиатуры неудобно, а биометрия «первый раз вхолостую,
второй раз срабатывает». Цель — цельный UX в одном окне и биометрия с первого раза.

### Почему именно так — техническая суть бага биометрии (важный урок)

**Причина бага:** в v2 автобиометрия запускалась через `std::thread::spawn` (фоновый поток).
Windows Hello — это системный API, который **привязан к UI-потоку / оконному контексту**.
При вызове из фонового потока:
- системное окно всплывает «без хозяина» (не привязано к нашему окну);
- первое прикладывание пальца закрывает системное окно, но результат не доходит до приложения;
- повторный запрос (уже из UI-потока по кнопке) срабатывает нормально.

Отсюда эффект «первый раз вхолостую, второй раз работает».

**Решение:** вызывать биометрию **из UI-потока** через событийный цикл Slint:
```rust
slint::Timer::single_shot(Duration::from_millis(400), move || {
    if ctrl.has_pin() && ctrl.biometric() == LockResult::Granted {
        if let Some(w) = ui_weak.upgrade() { let _ = w.hide(); }
    }
});
```
`Timer::single_shot` выполняет замыкание в UI-потоке через 400 мс — к этому моменту окно
уже показано и активно, и Windows Hello корректно привязывается к нему. Запрос один,
срабатывает с первого раза.

**Урок для журнала:** системные API (особенно биометрия, диалоги ОС) часто требуют вызова
из конкретного потока. В Rust соблазн «кинуть в фоновый поток, чтобы не морозить UI» —
но для системных диалогов это ломает привязку к окну. Правильный путь — событийный цикл UI.

### Почему встроенная клавиатура, а не отдельное окно
Заказчик явно попросил: клавиатура выезжает в том же окне, раздвигая его. Это и удобнее
(один фокус, нет «потерянного» второго окна), и проще в реализации (один компонент,
одно состояние). Отдельное окно в Slint — это второй `Window`, который легко теряет фокус.

### Про автовход
Убрали кнопку «ОК» — вход происходит автоматически на 4-й нажатой цифре. Это современный UX
(как на телефоне): меньше кликов, меньше мыслей. Реализация — в колбэке `digit_pressed`:
как только `buf.len() == 4`, сразу проверяем PIN.

## Этап 3 (продолжение). Блокировка v4 — фикс зависания (блокировка UI-потока)

### Симптом
При открытом системном окне Windows Hello клик по нашему окну (PIN или повторно «Отпечаток»)
вызывает **зависание намертво** («не отвечает»).

### Корень (диагноз архитектора)
В `windows_hello.rs` вызов `op.get()` **синхронно блокирует** вызывающий поток до ответа ОС.
В v3 этот вызов шёл из UI-потока (через `Timer::single_shot` и `on_biometric`). Значит:
- UI-поток заморожен на всё время диалога Hello → окно «не отвечает»;
- повторный клик пытается запустить второй `op.get()` в том же UI-потоке → **дедлок**
  (два синхронных ожидания WinRT в одном потоке).

Главное правило, которое мы нарушили: **нельзя блокировать событийный цикл UI ожиданием
системного диалога**.

### Решение (паттерн «блокирующая операция в фоне → результат в UI»)
1. `op.get()` выполняется в **отдельном потоке** (`std::thread::spawn`). UI-поток свободен,
   окно отзывчиво, клики обрабатываются.
2. Результат возвращается в UI-поток через **`slint::invoke_from_event_loop`** — только там
   можно трогать окно (`hide` при успехе, `set_error_text` при отказе).
   `slint::Weak` реализует `Send`, поэтому слабую ссылку можно переместить в фоновый поток
   и там вызвать `invoke_from_event_loop`.
3. **Флаг «идёт»** (`Arc<AtomicBool>`): перед запуском — `compare_exchange(false → true)`;
   пока `true`, повторные запросы игнорируются. Это убирает дедлок при любых кликах.
   Флаг сбрасывается в `false` по завершении (в `invoke_from_event_loop`).

```rust
fn request_biometric(controller, ui_weak, flag) {
    if flag.compare_exchange(false, true, ...).is_err() { return; } // уже идёт — выходим
    std::thread::spawn(move || {
        let result = controller.biometric();          // блокирует этот поток, не UI
        let _ = slint::invoke_from_event_loop(move || {
            flag.store(false, ...);                    // освободили флаг
            if let Some(w) = ui_weak.upgrade() {
                match result { Granted => { let _ = w.hide(); } Denied => w.set_error_text(...), }
            }
        });
    });
}
```

### Урок для журнала (важный)
- **Системные/блокирующие API (биометрия, диалоги ОС, сеть, диск) — в отдельный поток**,
  никогда не в UI-потоке. Иначе «не отвечает».
- **Окно трогаем только из UI-потока** — через `invoke_from_event_loop`. Из фонового потока
  напрямую трогать UI нельзя (и небезопасно).
- **Повторные запросы защищаем флагом** — иначе гонка и дедлок.
- Прошлая гипотеза «фоновый поток ломает Hello» была неверной. Реальная причина — блокировка
  UI-потока. Фоновый поток для `op.get()` — это и есть правильный паттерн.

### Про прошлые версии (краткая эволюция)
- v1: текстовое поле PIN, кнопка биометрии. Биометрия по кнопке, в UI-потоке — морозила UI.
- v2: валидация PIN, автобиометрия в `std::thread` — но результат не возвращался в UI корректно,
  «первый раз вхолостую».
- v3: автобиометрия через `Timer::single_shot` в UI-потоке — работало с первого раза, но
  **блокировало UI** (зависание при кликах).
- v4 (текущая): фоновый поток + `invoke_from_event_loop` + флаг «идёт» — UI отзывчив,
  биометрия с первого раза, дедлока нет.

## Этап 3 (продолжение). Блокировка v5 — активация окна Hello

### Проблема
Системное окно Windows Hello всплывало **в фоне** — приходилось кликать по нему мышкой,
чтобы приложить палец. Заказчик хочет: «Запустил → Приложил → Зашёл» без лишних кликов.

### Почему так происходит
Windows показывает запрос Hello как **модальное окно поверх окна, которое вызвало запрос**.
Если в момент вызова активно и на переднем плане **наше** окно — запрос наследует фокус и
всплывает активным. Если фокус на другом окне (например, на терминале, откуда запущен
`cargo run`) — Hello всплывает сзади.

### Решение
Перед запросом биометрии **принудительно поднять наше окно на передний план** через Win32 API:
```rust
let handle = ui.window().window_handle();           // slint::WindowHandle
let raw = handle.window_handle()?;                  // raw-window-handle: WindowHandle
if let RawWindowHandle::Win32(win32) = raw.as_raw() {
    let hwnd = HWND(win32.hwnd.get() as *mut _);
    unsafe {
        ShowWindow(hwnd, SW_SHOW);
        BringWindowToTop(hwnd);
        SetForegroundWindow(hwnd);
    }
}
```
Тогда модальный запрос Hello всплывает активным — палец прикладывается сразу.

### Технические детали (для журнала)
- **Дескриптор окна:** `slint::WindowHandle` реализует трейт `HasWindowHandle` из
  `raw-window-handle` 0.6. Нужна фича `raw-window-handle-06` у `slint` (добавили в `Cargo.toml`).
- **Win32 API:** `SetForegroundWindow`, `BringWindowToTop`, `ShowWindow` — нужны features
  `Win32_Foundation` и `Win32_UI_WindowsAndMessaging` у `windows` crate.
- **Только Windows:** всё под `cfg(windows)`, для других ОС — заглушка (CI собирается).

### Честная оговорка
Windows намеренно **ограничивает «кражу» фокуса** (`SetForegroundWindow` может быть отклонён ОС)
— защита от назойливых окон. Для только что запущенного пользователем приложения обычно срабатывает.
У собранного `.exe` (двойной клик) поведение лучше, чем у `cargo run` из терминала.
Если основной приём не сработает — запасные: `AllowSetForegroundWindow`, `FlashWindow`.

### Урок
- Системные диалоги (Hello, диалоги выбора файла и т.п.) привязаны к «активному окну».
  Чтобы они вели себя предсказуемо — **сначала делаем активным своё окно**.
- Доступ к нативному HWND в Rust-UI-фреймворках — через `raw-window-handle`. Это стандартный
  мост между UI-фреймворком и платформой.

## Этап 3 (продолжение). Блокировка v6 — финальная логика биометрии (по клику пользователя)

### Что произошло
В v5 мы попытались активировать окно через `SetForegroundWindow` перед автозапросом биометрии
при старте. На практике Windows **блокирует «кражу» фокуса из фона** — и Hello всё равно
всплывал сзади, нужно было кликать по нему мышкой.

### Решение (подсказано заказчиком — и оно правильное)
**Убрать автозапрос биометрии при старте.** Биометрия запускается **только по клику**
пользователя по кнопке «Отпечаток пальца».

Почему это работает: есть правило Windows — **«input-driven foreground»**. Приложение может
вывести окно на передний план, только если это происходит **в ответ на действие пользователя**
(клик/клавиша). Когда пользователь кликает по нашей кнопке — наше окно в этот момент **уже
активно** (он же по нему кликнул). Значит, системный запрос Hello всплывает поверх него
активным, палец прикладывается сразу, без тыканья по чужому окну.

### Финальный UX
- Запустил → видишь окно с кнопками «👆 Войти по отпечатку» и «Войти по PIN».
- Кликнул «Войти по отпечатку» → Hello всплывает активным → приложил палец → вошёл.
- Либо «Войти по PIN» → встроенная клавиатура → 4 цифры → автовход.

Формула: «Запустил → Кликнул Отпечаток → Приложил → Зашёл».

### Урок для журнала
- **Не борись с правилами ОС — используй их.** Windows запрещает фоновую кражу фокуса не
  просто так (защита от назойливых окон). Вместо «взлома» через `SetForegroundWindow` из фона —
  правильнее запустить действие по явному клику пользователя. Тогда правило «input-driven»
  работает на нас.
- Заказчик, не зная Rust, рассуждал об этом как инженер — и его догадка оказалась точнее
  моего первого решения. Это хороший пример того, почему архитектор должен слушать заказчика
  и дискутировать, а не слепо навязывать «технически правильное» решение.

### Что осталось от v4/v5
- Фоновый поток для `op.get()` + `invoke_from_event_loop` для результата — **сохранено**
  (нет зависания UI, нет дедлока).
- Флаг «идёт» (`AtomicBool`) — **сохранён** (защита от повторных запросов).
- `bring_window_to_foreground` (`SetForegroundWindow`) — **оставлен** как страховка
  (по клику он сработает корректно, окно уже активно).

## Этап 3 (продолжение). Блокировка v7 — AttachThreadInput, кнопка Назад, лимит попыток

### Что сделали (три задачи по отзыву заказчика)
1. **Усиление фокуса Hello** — трюк `AttachThreadInput`: временно «подключаем» ввод нашего
   потока к потоку текущего переднего окна, после чего `SetForegroundWindow` проходит.
   Дополнительно `SetActiveWindow` + `SetFocus`. Если и это не поможет — принимаем как
   ограничение ОС (решение архитектора: не биться бесконечно).
2. **Кнопка «Назад» (←)** в свободной ячейке клавиатуры — прячет клавиатуру, сбрасывает ввод,
   возвращает на главный экран блокировки (если передумал вводить PIN).
3. **Лимит 3 попыток PIN** — счётчик `AtomicU32`; после 3 неверных вводов приложение
   закрывается через `slint::quit_event_loop()`. При успехе счётчик сбрасывается.
   В UI: «Неверный PIN. Осталось попыток: N».

### Трюк AttachThreadInput (для журнала)
Windows запрещает «кражу» фокуса из фона, но если **объединить очереди сообщений** двух потоков
через `AttachThreadInput(our, fg, true)`, то `SetForegroundWindow` срабатывает. После —
отсоединяем (`AttachThreadInput(our, fg, false)`). Это известный обходной приём именно для
этой проблемы Windows. Честно: 100% гарантии нет (ОС может отказать), но это самое сильное
средство из доступных.

### Лимит попыток — безопасность
3 неверных PIN → закрытие. Это защита от подбора (хотя 4 цифры = 10000 вариантов, лимит
делает перебор бессмысленным за один запуск). Счётчик только для PIN, биометрию не считаем
(там ОС сама ограничивает попытки).

### Кнопка Назад — UX
Раньше, открыв клавиатуру, нельзя было вернуться без ввода. Теперь «←» возвращает на главный
экран. Маленькая, но важная деталь юзабилити — «всегда есть путь назад».

## Этап 3. Главный экран галереи — выбор папки и сетка миниатюр

### Что сделали
- Добавили crate **`rfd`** (Rust File Dialog) — системный диалог выбора папки (кнопка →
  открывается родное окно Windows, пользователь выбирает папку).
- Создали компонент **`GalleryScreen`** (в `lock.slint`, рядом с `LockScreen`):
  верхняя панель с заголовком, две кнопки выбора режима («Выбрать папку» и
  «Папка с подпапками»), статус-строка, прокручиваемая сетка миниатюр.
- `struct ThumbItem { file-name, image }` в Slint — элемент сетки.
- Функция `run_gallery()` в `ui/mod.rs`: связывает UI с ядром (scanner + thumbnails).
- `main.rs` после успешного входа открывает галерею (вместо заглушки).
- `Theme` вынесен в `theme.slint`, импортируется обоими экранами (DRY).

### Зачем
Это финальная часть MVP: после входа пользователь выбирает папку и видит свои фото
миниатюрами. Без этого «эксплорер» не эксплорер.

### Почему именно так — ключевые концепции

#### 1. Системный диалог выбора папки (rfd)
Вместо того чтобы просить пользователя печатать путь, используем системный диалог —
привычный и удобный. `rfd::FileDialog::new().pick_folder()` открывает родное окно Windows.
Это блокирующий вызов, поэтому — в фоновом потоке (как биометрию), результат — через
`invoke_from_event_loop`.

#### 2. Тяжёлые операции в фоновом потоке
Скан папки + генерация миниатюр (особенно для большой коллекции) — долго. Делаем в
`std::thread::spawn`, UI показывает «Сканирование...» и остаётся отзывчивым. Результат
возвращаем в UI-поток через `slint::invoke_from_event_loop` — тот же паттерн, что с биометрией.

#### 3. Миниатюры → Slint Image
Миниатюры из ядра — это `Vec<u8>` (RGBA). Slint хочет `slint::Image`. Преобразование:
```rust
let mut buf = SharedPixelBuffer::<Rgba8Pixel>::new(width, height);
for (dst, chunk) in buf.make_mut_slice().iter_mut().zip(data.as_chunks::<4>().0) {
    dst.r = chunk[0]; dst.g = chunk[1]; dst.b = chunk[2]; dst.a = chunk[3];
}
let image = slint::Image::from_rgba8(buf);
```
`as_chunks::<4>()` — разбивает `&[u8]` на `&[[u8; 4]]` (RGBA-пиксели) без копирования.

#### 4. ModelRc для динамического списка
Slint хранит списки в `ModelRc<T>`. Оборачиваем `Vec<ThumbItem>` в `slint::VecModel`,
затем в `ModelRc::new(vec_model)`. В разметке `for thumb[i] in root.thumbnails : ...`
автоматически перерисовывается при изменении модели.

#### 5. Hexagonal в действии
UI вызывает порты `PhotoScanner` и `ThumbnailProvider` из ядра — не лезет в детали
(`walkdir`, `image`, `rayon`). Ядро не знает про Slint. Это и есть чистая архитектура:
поменяй UI — ядро не трогай; поменяй реализацию сканера — UI не изменится.

### Про сборку нескольких .slint
`slint_build::compile` принимает один файл. Чтобы оба компонента (`LockScreen` и
`GalleryScreen`) были доступны — держим их в одном `lock.slint`. `Theme` вынесен в
`theme.slint` и импортируется через `import { Theme } from "theme.slint";`.

### Что увидит заказчик
После входа — окно галереи. Клик «Выбрать папку» → системный диалог → выбираешь папку
с фото → «Сканирование...» → появляются миниатюры в списке с именами файлов.
Статус: «Найдено фото: N». Это полноценный MVP: вход → выбор папки → просмотр миниатюр.

## Этап 4.2. Просмотр фото (viewer) — скорость: кэш, предзагрузка, downscale

### Что сделали
Клик по миниатюре открывает фото поверх галереи (overlay). Листание ←/→, закрытие Esc.
Главное внимание — **скорость** (заказчик требовал «архи-супер-быстро»).

### Три приёма ускорения

**1. Downscale при декодировании.** Фото с телефона — 12–50 мегапикселей. Экран — обычно
2–4 Мп. Держать и рисовать «сырой» огромный битмап бессмысленно. При загрузке уменьшаем
большую сторону до `VIEWER_MAX_SIZE = 2560` пикселей быстрым фильтром `Triangle`:
```rust
if img.width() > VIEWER_MAX_SIZE || img.height() > VIEWER_MAX_SIZE {
    img.resize(VIEWER_MAX_SIZE, VIEWER_MAX_SIZE, FilterType::Triangle)
}
```

**2. LRU-кэш в памяти.** Уже показанные фото храним в `lru::LruCache` (последние 20 штук),
ключ — путь к файлу. Повторное открытие — мгновенно, без чтения с диска.

**3. Предзагрузка соседей.** Пока смотришь фото N, в фоне уже грузятся N−1 и N+1
(`preload_neighbors`). Нажал стрелку — следующее фото уже в кэше, показывается без задержки.

### Почему `slint::Image` строим в UI-потоке
`slint::Image` — **не `Send`**, его нельзя передать между потоками. Поэтому фоновый поток
возвращает «сырые» данные `(Vec<u8>, width, height)` (они `Send`), а сам `Image` собираем
уже в UI-потоке через `invoke_from_event_loop`. `slint::Weak` при этом `Send` — его передавать можно.

## Этап 4.2b. Фикс краша и зависания + логирование + фуллскрин + фокус

> Этот раздел — честная история про две серьёзные ошибки и то, как мы их победили.
> Для «учебника» он особенно ценен: показывает типичные грабли многопоточного Rust.

### Проблема 1 — КРАШ при быстром листании (exit code 0xcfffffff)

**Симптом:** при быстром листании стрелками приложение падало.

**Причина — две сразу:**
1. **Отравленный (poisoned) Mutex.** В Rust, если поток **паникует**, держа `Mutex`, этот
   мьютекс помечается «отравленным». Любой последующий `.lock().unwrap()` на нём — тоже паника.
   А у нас фоновый поток мог паниковать на битом файле → каскад паник → `abort`.
2. **Лавина потоков.** Каждое нажатие стрелки плодило новый `std::thread::spawn`, плюс
   предзагрузка соседей — ещё потоки. При быстром листании — десятки, все декодируют мегабайты.

**Фикс:**
- `lock_or_recover()` — берёт блокировку даже у отравленного мьютекса:
  ```rust
  fn lock_or_recover<T>(lock: &Mutex<T>) -> MutexGuard<'_, T> {
      lock.lock().unwrap_or_else(|e| e.into_inner())
  }
  ```
  Лучше показать чуть устаревшее состояние, чем уронить всё приложение.
- `std::panic::catch_unwind` вокруг `image::open` — битый файл возвращает `Err`, а не панику.
- **Поколение загрузок** (`AtomicU64`): при каждом переключении номер увеличивается. Фоновый
  поток перед применением результата сверяет своё поколение — если устарело, молча отбрасывает.
  Это и убирает «мигание» чужими фото, и гасит смысл лавины.

### Проблема 2 — ЗАВИСАНИЕ «Не отвечает» (deadlock)

**Симптом:** открываю фото, кликаю по окну мышкой — приложение намертво виснет, «Не отвечает».

**Причина — классический deadlock на нереентерабельном Mutex.** Вот коварное место:
```rust
if let Some(cached) = lock_or_recover(&cache).get(&path).cloned() {
    // ... показываем фото ...
    preload_neighbors(photos, index, cache); // ← ТУТ
}
```
Тонкость Rust: временный guard от `lock_or_recover(&cache)` в заголовке `if let` **живёт до
конца всего блока**. А внутри вызывается `preload_neighbors`, который снова берёт **тот же**
`cache`-Mutex. `std::sync::Mutex` **не реентерабельный** — повторный захват на том же потоке
= вечная блокировка. UI-поток встал → «Не отвечает».

**Фикс — освобождать guard сразу:**
```rust
let cached_opt = lock_or_recover(&cache).get(&path).cloned(); // guard умер здесь
if let Some(cached) = cached_opt {
    // ... теперь cache свободен ...
    preload_neighbors(photos, index, cache); // deadlock невозможен
}
```
**Правило на будущее:** никогда не держи guard мьютекса, вызывая функцию, которая сама берёт
тот же мьютекс.

### Система логирования (`src/logging.rs`)

Заказчик справедливо сказал: «хватит гадать, сделай логи». Собственная реализация трейта
`log::Log`:
- Пишет в файл `%TEMP%/photo_explorer/photo_explorer.log` и дублирует в stderr.
- **panic hook** (`std::panic::set_hook`): паника **любого** потока пишется в лог —
  поток, адрес в коде, текст. Теперь падение всегда оставляет след.
- Логи расставлены по всему пути: старт, вход, скан (папка, результат), viewer
  (открытие/кэш/декодирование+время/поколение/фуллскрин/ошибки).

Почему своя реализация, а не `env_logger`: не хотели тянуть лишние зависимости ради файла —
трейт `Log` простой, пишем сами (учебная ценность: видно, как работает фасад `log`).

### Фуллскрин «как в играх»

Раньше мы по ошибке разворачивали **всё окно**. Заказчик поправил: приложение должно быть
обычным окном, а на весь экран — **только фото**. Решение:
- `window().set_fullscreen(true)` — при **открытии** фото (на активном мониторе).
- `window().set_fullscreen(false)` — при **закрытии** (возврат в оконный режим).

### Фокус сразу, без второго клика

`FocusScope` сделали **корнем** overlay (а не вложенным элементом в конце списка). Он занимает
весь экран, `init => self.focus()` срабатывает надёжно при каждом открытии. `TouchArea` фона и
кнопки — его дети, они не перехватывают клавиатурный фокус. Стрелки и Esc работают мгновенно.

### Чему научились
- Многопоточность в Rust безопасна по памяти, но **deadlock и паники-в-потоках** — всё ещё
  твоя ответственность.
- Guard мьютекса в `if let`/`match` живёт дольше, чем кажется — освобождай явно.
- Логи — не роскошь: первый же лог показал бы, где именно встало.

## Этап 4.3. Листание фото — долгая охота за «затупом» (v1 → v8)

> Это самый поучительный раздел журнала. Он показывает, как **одна и та же жалоба**
> («тормозит при листании») может иметь **несколько разных причин**, и как важно
> не гадать, а **измерять** (логи). Мы прошли 8 итераций — каждая убирала один слой проблемы.

### Что хотел заказчик
- Колесо мыши листает фото; стрелки ←/→ тоже.
- **Удержание** стрелки → быстрое «моргание», как при очень быстром ручном нажатии.
- ЛКМ больше не закрывает (освободить под зум); закрытие — Esc и ✕.
- Кнопки управления (× ← →) автоскрываются через 2.5с.

### Хронология багов и фиксов

**v1–v2 (debounce 60→200мс).** Первая мысль: «тормозит — отложим загрузку».
Поставили таймер-дебаунс. Стало **хуже**: debounce тормозил вообще всё (даже
мгновенный показ из кэша), а старое чёткое фото накладывалось на новую миниатюру
(«полоски сверху-снизу»). **Урок:** дебаунс не к месту — лечили симптом, не причину.

**v3 (откат debounce + очистка слоя).** Вернули мгновенную загрузку, при листании
очищаем старое фото. «Полоски» ушли, но при **удержании** всё ещё затуп.

**v4–v5 (debounce только мимо кэша, 150→300мс).** Логично: кэш — мгновенно, тяжёлое
декодирование — с задержкой. Догон уменьшился, но не исчез. **Урок:** полумера.

**v6 (ОДИН воркер-поток вместо spawn-на-задачу).** Нашли первый настоящий корень:
на **каждое** нажатие создавался новый ОС-поток (`std::thread::spawn`), плюс
`preload_neighbors` плодил ещё. При удержании — **сотни потоков**, ОС захлёбывался.
Заменили на классический **producer-consumer**: один постоянный воркер + канал
`mpsc`. UI шлёт задачи, воркер дренирует очередь (берёт последнюю актуальную),
декодирует одно фото. Затуп уменьшился — но не до конца.

**v7 (кэш готовых `slint::Image`) — ПОБЕДА.** Заказчик задал ключевой вопрос:
«почему быстрое ручное нажатие работает, а удержание — нет?». Чтобы не гадать,
**прочитали лог** (`./logs/photo_explorer.log`). И увидели: даже из кэша на **каждый**
кадр UI-поток строил `slint::Image` из сырого RGBA **попиксельным копированием**
(до 26 МБ на фото!). 20–30 событий/сек × десятки МБ = гигабайты копирования
в главном потоке → затуп. Ручное нажатие реже → UI успевал.
**Фикс:** кэшировать **готовый** `slint::Image` (его `clone` дешёвый — внутри `Rc`),
а не сырой RGBA. Повторный показ = `set_viewer_image(img.clone())` без копирования.
Затуп **исчез** — заказчик подтвердил.

**v8 (убрали индикатор «Загрузка»).** Заказчик: «зачем это слово вообще?». Он был
прав — при мгновенном показе из кэша и миниатюре-плейсхолдере индикатор избыточен,
да ещё и залипал. Удалили полностью (принцип **KISS**).

### Технические приёмы, которые тут родились
- **Producer-consumer**: один воркер-поток + `mpsc::channel` вместо потока-на-задачу.
  `slint::Image` не `Send` — строим его в UI-потоке; `Weak` и сырые байты `Send` — их шлём.
- **Дренирование очереди** (`drain_to_last`): при наплыве задач берём только последнюю
  актуальную, промежуточные пропускаем (дёшево — это пути, не декодирование).
- **Два кэша**: сырой RGBA (`Arc<Mutex>`, для воркера, `Send`) + готовые `slint::Image`
  (`Rc<RefCell>`, только UI-поток, не `Send`). Клон `Image` дешёвый.
- **Поколение (`AtomicU64`)**: устаревшие результаты отбрасываются при быстром листании.
- **Логи в `./logs/`** (на время разработки, в `.gitignore`) — именно лог указал на
  истинную причину v7, которую мы 6 итераций не видели.

### Главный урок
**Не гадай — измеряй.** Шесть итераций мы чинили «правдоподобные» причины (debounce,
потоки) и каждый раз ошибались частично. Один взгляд в лог сразу показал настоящее
узкое место (копирование RGBA в UI-потоке). Подробное логирование окупилось сполна.

## Этап 4.3e. Авто-скип битых файлов — «залипание» кадра на большой папке

**Симптом.** Заказчик добавил большую папку `C:\Kirpi\Новая папка(6)` и заметил
«странный баг»: при листании некоторые кадры **залипают** — фото не меняется, будто
стрелка не сработала, хотя счётчик индекса уже ушёл вперёд.

**Диагностика по логу** (`logs/photo_explorer.log`, строки 12099, 12172, 12220…):
среди файлов с расширением `.png` попадаются **битые** — содержимое не является
валидным PNG (ошибка `Format error decoding Png: Invalid PNG signature`). Сканер
включил их в список по расширению, а декодер `image::open` их не берёт.

**Корень бага.** В воркере при `Err` только писался лог и `set_error_text`, но
`viewer-image` **не обновлялся**. Индикатор «Загрузка» мы убрали ещё в v8 (бесполезен
и залипал), поэтому на битом файле на экране просто оставалось предыдущее фото без
всякой реакции. В большой папке таких битых `.png` много → эффект заметен.

**Решение (по согласованию с заказчиком).** Битый файл **автоматически пропускается** —
переход к следующему годному фото в текущем направлении листания.

### Что сделали

1. **Направление листания** — `last_direction: Arc<AtomicI32>` (+1 вперёд / −1 назад).
   Колбэки `on_viewer_next` / `on_viewer_prev` / `on_open_viewer` выставляют его.
   Скип идёт в ту же сторону, куда листал пользователь.

2. **Воркер при `Err`** не просто пишет лог, а вызывает UI-колбэк `request-skip(next, dir, depth)`:
   `next = index + dir`, `depth = skip_depth + 1`.

3. **Защита от зацикливания** — `skip_depth` в `LoadTask::Photo`. Если перепробовали
   больше, чем файлов в списке (все битые) — стоп, показываем плашку `viewer-error`
   «Файл не открывается» на чёрном фоне. `next_valid_index` клампит по границам и
   возвращает −1 на краю — тоже стоп с плашкой.

4. **Не-`Send` `Rc`-кэш** нельзя тащить в воркерское замыкание (`invoke_from_event_loop`).
   Поэтому скип инициирует воркер через колбэк `request-skip`, а обработчик
   `on_request_skip` в UI-потоке (где `Rc` доступен) шлёт новую задачу в канал.

5. **Сброс `viewer-error`** при каждом успешном показе (ветки UI-кэша, RGBA-кэша
   и успешного декода) — чтобы ошибка не «прилипала» к следующему хорошему фото.

6. **Чистая функция** `next_valid_index(next, dir, count)` вынесена на уровень модуля
   (`pub fn`) — легко тестировать без UI.

### Тесты (`tests/viewer_skip_tests.rs`, 7 штук)

- `next_valid_index_forward_in_bounds` — скип вперёд внутри списка.
- `next_valid_index_backward_in_bounds` — скип назад внутри списка.
- `next_valid_index_forward_at_edge_returns_minus_one` — скип за край вперёд → −1.
- `next_valid_index_backward_at_start_returns_minus_one` — скип за край назад → −1.
- `next_valid_index_empty_list_returns_minus_one` — пустой список.
- `next_valid_index_single_file_no_neighbors` — 1 файл: любой скип → −1.
- `broken_png_does_not_decode` — файл `.png` с мусорным содержимым → `image::open` → `Err`.

**Итог:** `cargo fmt` чист, `clippy` чист, **35 тестов зелёные** (28 + 7 новых).
Битые файлы больше не залипают — листание плавно проходит их, показывая следующий
годный кадр. Если все файлы в папке битые — видим явную плашку, а не «зависшее» фото.

## Этап 4.3f. Фикс «прыжка» при зуме — конфликт pan и зума + кламп «край в край»

**Симптом.** Заказчик: «во время увеличения вроде увеличивает, но иногда вдруг
куда-то прыгает и фото улетает за границы монитора или резко смещается».

**Диагноз (две причины).**

1. **Зум и pan «дерутся» за один и тот же offset.** Зум к курсору работает при
   зажатой ЛКМ (`scroll-event` → `if self.pressed`), но pan тоже срабатывает на
   зажатой ЛКМ. Схема pan была «от замороженного старта»: при нажатии ЛКМ
   запоминались `pan-start-mouse` и `pan-start-offset`, при движении offset
   пересчитывался как `pan-start-offset + (mouse − pan-start-mouse)`. Но зум
   колесом МЕНЯЕТ offset (формула зума к курсору), а `pan-start-offset` остаётся
   старым. Первый же `pointer-move` после зума (даже микродрожание мыши на 1px)
   ОТКАТЫВАЛ offset к до-зумному значению + дельта → фото резко «прыгало» и с
   накоплением уходило за экран.

2. **Нет ограничения смещения.** Ни зум, ни pan не клампили offset — фото в
   принципе можно было увести целиком за край экрана (чёрное поле).

**Решение (согласовано с заказчиком: кламп «край в край», как в классических
просмотрщиках — фото упирается краем в край экрана).**

1. **Инкрементальный pan** (вместо «от старта»): на каждом `pointer-move` добавляем
   к offset дельту между СОСЕДНИМИ позициями мыши (`mouse − prev-mouse`), `prev-mouse`
   обновляется на каждом move. Схема не опирается на замороженный offset — зум и pan
   больше не конфликтуют. Pan вынесен в колбэк `viewer-pan-by(dx, dy, vw, vh)`.

2. **Кламп «край в край»** — чистая функция `clamp_offset(offset, zoom, viewport)`:
   максимум смещения, при котором фото ещё ЗАКРЫВАЕТ viewport по оси,
   `max = (vp·zoom − vp)/2`; при zoom=1 максимум 0 (вписанное фото не двигается).
   Применяется и в `on_viewer_zoom_at` (теперь slint передаёт размеры viewport
   vw/vh), и в `on_viewer_pan_by`.

### Тесты (`tests/viewer_skip_tests.rs`, +5 → 40 всего)

- `clamp_offset_center_stays` — центр (0) не трогается.
- `clamp_offset_zoom_one_forces_zero` — zoom=1: любое смещение → 0.
- `clamp_offset_edge_limit` — viewport 1000, zoom 2 → max 500; смещение 700 клампится к 500.
- `clamp_offset_inside_bounds_untouched` — внутри диапазона не меняется.
- `clamp_offset_negative_viewport_safe` — вырожденный viewport (≤0) → 0.

**Итог:** `cargo fmt` чист, `clippy` чист, **40 тестов зелёные** (35 + 5 новых).
Зум больше не «прыгает»: точка под курсором остаётся под курсором, а увеличенное
фото всегда закрывает экран — упирается краем в край, как в классических просмотрщиках.

## Этап 4.3g. Скип через один + кламп по картинке (contain-fit)

**Симптомы по итогам теста заказчиком.**
1. «При листании через какое-то время в фоне одно фото горит, а показывается другое».
2. «Увеличение за границы экрана уводит».

**Диагностика по логу** (`logs/photo_explorer.log`):

1. **Скип шёл ЧЕРЕЗ ОДИН.** В хвосте лога серия: битый 742 → скип на 744 → 746 → …
   (шаг 2). Причина — двойное прибавление направления: воркер в `Err`-ветке шлёт
   `request-skip(index + dir)`, а обработчик `on_request_skip` вызывал
   `next_valid_index(next_index, dir, count)`, который прибавлял `dir` ЕЩЁ РАЗ.
   Итог: при серии битых перепрыгивались и годные файлы — отсюда «показывается
   не то фото» и рассинхрон миниатюры-фона с чётким фото.

2. **Кламп считался по ЭЛЕМЕНТУ, а не по КАРТИНКЕ.** Элемент Image имеет размер
   `vp*zoom`, но картинка внутри вписана (contain-fit) и у узких/широких фото
   МЕНЬШЕ элемента. Кламп «элемент закрывает экран» не гарантирует «картинка
   закрывает экран»: узкое фото 480×600 на экране 1536×864 при zoom 10 — элементный
   max_x = 6912, а половина картинки всего 3456 → картинку можно было утащить
   ЦЕЛИКОМ за экран (чёрный экран). Это и есть «увеличение уводит за границы».

3. **Дыра prev-mouse.** `pointer-event down` записывал `prev-mouse` только при
   `zoom > 1`. Сценарий «зажал ЛКМ при zoom=1 → зазумил колесом → двинул мышь»
   давал pan-дельту от устаревшего (0,0) → фото прыгало к краю.

**Решение.**

1. **Фикс скипа:** `on_request_skip` использует присланный воркером `next_index`
   КАК ЕСТЬ — только проверяет границы (`0 ≤ next_index < count`). `dir` остался
   в сигнатуре колбэка (помечен `_dir`), но больше не прибавляется повторно.

2. **Кламп по картинке:** `clamp_offset` теперь знает размеры КАРТИНКИ:
   `contain_scale = min(vp_w/iw, vp_h/ih)` — во сколько раз картинка вписана при
   zoom=1; размер картинки на экране = `img * contain_scale * zoom`. Если по оси
   картинка меньше viewport — двигать нельзя (max=0), иначе `max = (size − vp)/2`.
   Размеры картинки (`viewer-img-w/h`) пробрасываются из slint во все три места
   показа (UI-кэш, RGBA-кэш, декод воркера).

3. **prev-mouse при любом нажатии ЛКМ** (не только zoom>1) — устраняет прыжок
   после «зажал → зазумил → двинул».

### Тесты (14 в `viewer_skip_tests.rs`, 42 всего)

Новые: `clamp_offset_narrow_image_x_axis_locked` (узкая 480×600 в 1536×864:
по X при zoom 10 max ≈ 2688, по Y ≈ 3888 — float-сравнение с допуском) и
`clamp_offset_narrow_image_small_zoom_locked` (при малом zoom узкая картинка
по X меньше экрана → max=0, двигать нельзя).

**Итог:** `cargo fmt` чист, `clippy` чист, **42 теста зелёные**. Скип идёт строго
по одному файлу; увеличенное фото нельзя увести за экран — даже узкие картинки
упираются краем в край или стоят по центру, если меньше экрана.

## Этап 4.7. Проекты и недавние — сессионное хранилище

**Зачем.** Заказчик: «одна папка 8 файлов, другая 8000 — пока вторую просканирует,
пройдёт много времени. Чтобы каждый раз не тратить время… нужно то, что было
прошлый раз, открыть из микрохранилища». Плюс: сессии-историю нужно именовать,
как внутренние проекты, и видеть недавние (recent) даже без сохранения.
**ГЛАВНОЕ требование: открытие сессии должно быть БЫСТРЫМ — не медленнее скана.**

### Архитектура (Hexagonal)

- **Порт `SessionStore`** (ядро, `core/ports.rs`): `summaries`, `load`, `save`,
  `delete`, `find_by_folder`. Ядро не знает про JSON.
- **Адаптер `JsonSessionStore`** (`session/mod.rs`): один JSON на сессию
  (`%LOCALAPPDATA%/photo_explorer/sessions/<id>.json`) + лёгкий `index.json`
  (только id/имя/путь/время — стартовый экран рисуется мгновенно, без чтения
  полных сессий с 8000 фото). Запись атомарна (tmp → rename).
- **Модели** (`core/models.rs`): `Session` (id, имя, папка, режим, fingerprint,
  список `Photo`, last_opened, is_project) и `SessionSummary`. В `Photo` добавлено
  поле `modified` (unix-секунды) — нужно для fingerprint; всё сериализуется serde.

### Fingerprint — «папка не менялась» без чтения файлов

`fingerprint_of(photos)` — хеш отсортированного списка `(путь, размер, mtime)`.
Только метаданные, тела файлов не читаются: обход 8000 записей — секунды против
минут полного скана с миниатюрами. Сортировка делает отпечаток независимым от
порядка обхода ФС. Ловит добавление/удаление/замену/переименование.
`diff_photos(old, new)` — инкрементальная разница: «добавили 8 файлов в папку
из 8000 — обрабатываем только эти 8».

### UX: экран «Старт» после входа

После биометрии/PIN: слева «Проекты» (именованные), справа «Недавние» (recent,
автоматом). Кнопки ✎ (переименовать — Slint-диалог с TextInput) и 🗑 (удалить).
Клик по записи → **мгновенное открытие**: список фото из JSON, миниатюры из
дискового кэша (с прошлого раза), ноль ожидания.

### Быстрое открытие + фоновая проверка (4.7d)

1. Читаем `<id>.json` → сразу показываем галерею из кэша миниатюр.
2. ФОНОМ сканируем папку (метаданные) и сверяем fingerprint:
   - совпал → ничего не делаем (лог: «кэш актуален»);
   - изменился → `diff_photos` → миниатюры ТОЛЬКО для новых/изменённых →
     обновляем модель и сессию в хранилище. Показ не блокируется ни на шаг.

### Тесты (10 новых, 52 всего)

Юнит (`session/mod.rs`): fingerprint стабилен при перестановке; меняется от
размера/mtime/добавления/удаления; diff возвращает только новые/изменённые.
Интеграционные (`tests/session_tests.rs`): save→load roundtrip; summaries
сортированы свежие-сверху; upsert не плодит дубли; delete чистит файл и индекс;
find_by_folder по пути+режиму; NotFound для отсутствующей; Corrupted (не паника)
для битого index.json.

**Итог:** fmt/clippy чисты, **52 теста зелёные**. Папка сканируется один раз;
повторный вход — мгновенный, с фоновой проверкой актуальности и инкрементальным
доссканом только разницы.

## Этап 4.3h. Скип без сверки поколения — наложение двух кадров

**Симптом.** Заказчик: «полистал взад-вперёд, и в какой-то момент в фоне
показал кадр и поверх второй — опять та же фигня».

**Диагностика по логу** (сессия 2026-10-29 23:47, строки 21882-21894):
пользователь на битом index=15 листает prev → воркер шлёт `request-skip` →
в этот же момент пользователь жмёт next → скип приходит с УСТАРЕВШИМ индексом
и всё равно показывает свой кадр. Обычная загрузка такой результат отбрасывает
(сверка `generation`), а **скип — нет**: `on_request_skip` не проверял
поколение вообще. Устаревший скип строил свой Image поверх актуального →
наложение двух разных кадров.

**Фикс (минимальный, по выбору заказчика):** воркер при `Err` передаёт своё
`my_gen` в `request-skip` (4-й параметр колбэка); обработчик первым делом
сверяет поколение — если пользователь ушёл дальше, скип игнорируется, ровно
как устаревший результат обычной загрузки.

**Итог:** fmt/clippy чисты, **52 теста зелёные**. Гонка «скип против ручного
листания» закрыта: устаревший скип больше не накладывает кадр.

## Этап 4.3i. Двойной слой изображения — радикальный фикс рассинхрона

**Симптом.** После фикса 4.3h заказчик снова увидел тот же глюк: «в фоне
один кадр, поверх второй» при быстром листании туда-сюда на битых файлах.

**Диагностика (настоящая причина).** Во вьюере было ДВА независимых
`Image`-слоя: нижний `viewer-thumbnail` (миниатюра, мгновенный моргание)
и верхний `viewer-image` (чёткое фото). Это два РАЗНЫХ свойства, которые
пишутся в разные моменты и никак не связаны между собой. Проверка
`generation` (4.3h) защищала только чёткое фото, но не связку «миниатюра +
чёткое» как единое целое: при быстром листании порядок записей сбивался —
миниатюра показывала кадр N, а старое чёткое «залипало» поверх с кадром N±1.
Два слоя = два источника истины = рассинхрон возможен по построению.

**Фикс (радикальный, по выбору заказчика): один слой.**
- Убрали `viewer-thumbnail` полностью (свойство и нижний `Image` в Slint).
- Миниатюра при листании пишется в ТОТ ЖЕ `viewer-image`, затем чёткое
  фото перезаписывает его. Один источник — два кадра одновременно
  показаться физически не могут.
- **Единое поколение на переход:** раньше `generation.fetch_add` жил внутри
  загрузки; теперь инкремент один раз на переход, и это же `my_gen` делят
  миниатюра и чёткое. Обе записи в слой сверяются с одним поколением.
- Убрали промежуточную очистку `set_viewer_image(default)` перед миниатюрой
  (при одном слое она давала бы чёрный кадр-вспышку): миниатюра нового кадра
  сама первый кадр перехода.
- Миниатюра выставляет `viewer-img-w/h` по своему размеру — кламп зума
  (contain-fit) считается корректно ещё до прихода чёткого кадра (у миниатюры
  то же соотношение сторон, DPI в формуле сокращается).

**Рефакторинг заодно (DRY/KISS):** схема перехода «поколение → миниатюра →
чёткое» была скопирована в 4 колбэках (open/next/prev/skip). Вынесли её в
ЕДИНЫЙ метод `switch_to_photo` на новом контексте `ViewerCtx` (всё состояние
вьюера в одной структуре: фото, кэши, поколение, направление, канал воркеру).
Это заодно убрало предупреждение clippy `too_many_arguments` (9 аргументов
у старой `request_viewer_load`) — без `#[allow]`, по-настоящему.

**Итог:** fmt/clippy чисты, **52 теста зелёные**. Рассинхрон «в фоне один,
поверх другой» устранён по построению: слой один, поколение одно на переход,
все записи сверяются с ним. Ожидание ручного теста заказчиком.

## Этап 4.4a. Режимы листания per-project + фоновая загрузка сессии

Заказчик после приёмки 4.3i принёс два бага и одну фичу.

**Баг 1 — «открываю сессию с 8-9к файлов — затупливает на 10-60 сек».**
Диагностика по коду: в `on_open_session` миниатюры ВСЕХ фото строились
синхронно в UI-потоке (`thumbs.thumbnails(&session_photos)` на 10653 файла +
построение 10653 `slint::Image`). Главный поток блокировался на десятки
секунд — окно «висло». Тот же путь, от которого ушли в галерее воркером,
но в открытии сессии он остался синхронным.

**Баг 2 — «зажимаю влево, доходит до 1 фото и чёрный экран, как будто
листает в минус».** Лог подтвердил (строки 25611-25614): `prev → index=0`,
затем `prev → index=10652` — листание было ВСЕГДА циклическим: на первом
фото prev заворачивал на ПОСЛЕДНЕЕ (10652), а там тяжёлые кадры (в логе
декод 3840x3680 PNG занял 9.9 сек) → чёрный экран на секунды. Пользователь
читал это как «ушёл в минус в пустоту».

**Фича — настройки листания per-project.** Три режима в панели ⚙:

| Режим | Поведение на границе |
|-------|----------------------|
| **До края** (edge, по умолчанию) | на первом/последнем фото — стоп |
| **Циклично** (cycle) | заворачивает на противоположный край |
| **Случайно** (random) | обе кнопки выбирают случайной кадр из списка |

Решения заказчика: по умолчанию «до края» (чинит баг 2); в random обе
кнопки (next и prev) случайные — проще и предсказуемо.

**Реализация.**
- `Session.nav_mode: String` с `#[serde(default)]` — старые JSON читаются,
  пустая строка = edge. Настройка per-project: переживает перескан
  (upsert сохраняет прежний режим) и перезапуск.
- `NavMode` (Edge/Cycle/Random) + стандартный трейт `FromStr` (пустая
  строка/мусор → Edge) + `as_str()` для сохранения.
- Чистая функция `nav_next(cur, count, dir, mode) -> Option<i32>`:
  edge — `None` за краем (стоп, ничего не грузим); cycle — заворот;
  random — `rand::thread_rng().gen_range(0..count)`.
- `ViewerCtx` получил `nav_mode: Rc<RefCell<NavMode>>`; `on_viewer_next`/
  `on_viewer_prev` считают индекс только через `nav_next`.
- Панель ⚙: заглушка заменена на три переключателя (компонент `NavOption`
  верхнего уровня — inline-`component` внутри элемента Slint не парсится);
  `on_set_nav_mode` обновляет контекст, UI и сессию.
- **Фон-загрузка сессии:** `on_open_session` теперь мгновенно показывает
  статус «Открываю проект…» и выставляет режим, а ОДИН фоновый поток со
  строгим порядком делает: миниатюры → `set_thumbnails` через
  `invoke_from_event_loop` → сохранение last_opened → обновление стартового
  экрана → fingerprint-проверка (4.7d). UI-поток не блокируется.

**Итог:** fmt/clippy чисты, **63 теста зелёных** (+11 на `nav_next`/`NavMode`:
edge-стоп на обеих границах, cycle-завороты, random в диапазоне, count=0/1,
парсинг строк). Ожидание ручного теста заказчиком.

## Этап 4.4b. Порционная загрузка галереи — батчи миниатюр

**Симптом.** После 4.4a заказчик: «открываю предыдущую папку — окно открыто,
но всё равно тупит 30-40 сек, будто пытается прочитать все 8к фото. Зачем?
Второй раз должен открывать моментально».

**Диагностика (архитектура тормозов, простыми словами).** 4.4a убрал фриз
на этапе ЧТЕНИЯ миниатюр (они ушли в фон), но остался второй фриз — на этапе
ПОКАЗА. При открытии проекта фоновый поток строил ВСЕ 10653 миниатюры,
а потом ОДНИМ куском отдавал их в `set_thumbnails`. Дальше Slint-сетка
(`for thumb[i] in thumbnails` внутри Flickable — без виртуализации)

тысяч. Плюс 10653 PNG-миниатюры читались и декодировались с диска подряд,
даже из тёплого кэша. Итого «тупит», хотя окно уже на экране.

**Фикс — порционная (batch) загрузка, по предложению заказчика:**
- Первый батч **200** миниатюр — заменяет модель, сетка оживает сразу,
  viewer готов к листанию (миниатюры-плейсхолдеры для первых фото есть).
- Остальные — батчами по **150**, добавляются в ТУ ЖЕ модель через
  `invoke_from_event_loop` (скролл не сбрасывается), между батчами пауза
  30 мс — UI успевает отрисовать кадр, не давится одним куском.
- Фон грузит ДО ПОЛНОЙ модели (не только видимое): через пару секунд
  миниатюра-плейсхолдер есть для ЛЮБОГО индекса — скоростной viewer
  из 4.3 не пострадал (моргание сохраняется).
- `gallery_gen` — поколение галереи: открыли другой проект → батчи
  старого отменяются (не подмешиваются в чужую сетку).

**DRY-бонус:** построение карточки `ThumbItem` из RGBA копировалось в
3 местах (скан, открытие сессии, досскан) — вынесено в `thumb_item_from`;
порционный путь — единая `load_thumbs_batched`, все три пути (первый скан,
открытие сессии, досскан по fingerprint) теперь ходят только через неё.
`scan_and_show` больше не строит миниатюры всем списком — только скан
метаданных, показ через ту же порционную функцию.

**Технический нюанс:** `ThumbItem` содержит `slint::Image` (не-Send) —
через `invoke_from_event_loop` переносится только чистый RGBA
(`Vec<Thumbnail>`, Send), карточка строится уже в UI-потоке.

**Итог:** fmt/clippy чисты, **63 теста зелёных** (состав не менялся —
перестройка пути показа). Ожидание ручного теста заказчиком: повторное
открытие 10653 — окно отзывчиво сразу, сетка наполняется батчами в фоне.

## Этап 4.4c. Random через перемешанный список — честный «назад»

**Симптом.** Random 4.4a вёл себя странно: «нажимаю стрелку — грузит фото
и тут же заменяет его другим; нажимаю назад — должно открыться предыдущее
просмотренное, а открывается одно и тут же заменяется каким-то иным».

**Причина.** Каждое нажатие вызывало `gen_range` — НОВОЕ случайное число.
«Назад» не мог вернуть просмотренное: истории не существовало, порядок не
был зафиксирован. Любой повторный тик (предзагрузка, скип битого) давал
новый случайный кадр, который «заменял» только что открытый.

**Фикс — идея заказчика:** «взять этот json и просто мешать в нём позиции
рандомно, номера — листая стрелками, я всё равно увижу те, что уже
просмотрел». При включении random строим ПЕРЕМЕШАННЫЙ список индексов
(биекция 0..count, каждый ровно раз) — ОДИН раз. Листаем по нему как по
обычному: next = следующая позиция списка, prev = предыдущая. Порядок
фиксирован → «назад» честно возвращает просмотренное.

**Реализация.**
- Чистые функции: `shuffled_order(count)` — перемешанная перестановка;
  `nav_random_next(order, pos, dir)` — шаг по списку (стоп на краях, как
  в edge). `nav_next` для Random оставлен как страховочная edge-ветка
  (в колбэках random идёт через `nav_random_next`).
- `ViewerCtx`: `shuffle_order: RefCell<Option<Vec<i32>>>` (None вне random)
  + `shuffle_pos: Cell<i32>` — ПОЗИЦИЯ в списке (не индекс фото; индекс
  фото по-прежнему в `viewer-index`, показ/загрузка не изменились).
- `ViewerCtx::set_nav(mode)`: random → строит список (старт — позиция
  текущего фото), edge/cycle → сбрасывает. Вызывается из ⚙ и при открытии
  сессии (режим из проекта применяется автоматически).
- `on_viewer_next`/`on_viewer_prev`: в random ходят по списку, границы —
  стоп (как edge). Смена режима в ⚙ мгновенно перестраивает список.

**Тот же список — фундамент будущего слайд-шоу:** автопоказ = автоматический
next по тому же порядку (обычному или перемешанному) поверх таймера.

**Итог:** fmt/clippy чисты, **66 тестов зелёных** (+3: биекция перестановки,
честный prev/next по списку, пустой список). Ожидание ручного теста.

## Этап 4.4c-2. Авто-скип битых в random — по перемешанному списку

**Симптом (повторный тест заказчика).** «Нажимаю стрелку — открывает
какое-то фото и тут же меняет его на следующее».

**Диагностика по логу (18:08:24, строки 27935-27952).** Random дал позицию
с фото #1531 — оно битое. Авто-скип (4.3e) искал годное ЛИНЕЙНО:
1531→1532→1533→1534→1535, игнорируя перемешанный порядок. Визуально кадр
«сам сменялся» на линейного соседа; `shuffle_pos` оставался на позиции 1531,
пока показывался 1535 — рассинхрон. В папке заказчика целые серии битых
(WebP с расширением .jpg: «Illegal start bytes:5249»), поэтому random
попадал в них постоянно.

**Фикс.** В random авто-скип идёт ПО ПЕРЕМЕШАННОМУ СПИСКУ:
- `on_request_skip` при Random берёт следующую позицию порядка через
  `nav_random_next(order, shuffle_pos, dir)` — не линейного соседа;
  `shuffle_pos` синхронно обновляется (всегда соответствует показанному).
- `dir` для скипа = направление последнего листания (воркер уже передаёт
  его в request-skip; в random это направление по списку).
- Край списка при серии битых — плашка, как в edge.
- Заодно: открытие фото КЛИКОМ из галереи в random теперь синхронизирует
  `shuffle_pos` с открытым фото (раньше next/prev считали от старой позиции).

**Итог:** fmt/clippy чисты, **66 тестов зелёных** (состав не менялся —
правка в обработчике скипа; логика списка уже покрыта тестами 4.4c).
Ожидание ручного теста: random на битых сериях показывает годное
случайное фото, кадр не «убегает», prev/next честные.

## Этап 4.4c-3. Broken-set — битые исключены из навигации

**Симптом (третья итерация).** «Нажимаю стрелку — открывает какую-то
миниатюрку, потом иное фото в хорошем качестве». Всё то же.

**Почему прошлые фиксы не помогали.** Я чинил механику скипа (4.4c-2:
скип по списку), но не убирал ИСТОЧНИК: в папке заказчика ОЧЕНЬ много
битых файлов (целые серии WebP с расширением .jpg — «Illegal start
bytes:5249»). Random постоянно попадал в них: показывалась миниатюра
битого → воркер не декодировал → скип уводил на другой кадр. Пользователь
каждый раз видел «миниатюра A → чёткое Z». В edge это незаметно (скип на
соседа), в random бросается в глаза (прыжок в другое место списка).

**Фикс (Вариант 2, по выбору заказчика) — битые исключаются из навигации:**
- `ViewerCtx.broken: Rc<RefCell<HashSet<i32>>>` — множество битых индексов,
  пополняется в `on_request_skip` (воркер сообщил об ошибке декода).
- `nav_next` (edge/cycle) и `nav_random_next` (random) принимают `broken`
  и ПРОПУСКАЮТ битые: листание шагает мимо них, не грузя заведомо битое.
  Cycle обходит весь список; если всё битое — None (плашка).
- `on_request_skip` помечает битый индекс ДО выбора цели скипа; в edge/cycle
  цель тоже проверяется против broken (шагаем дальше, пока годное).
- `switch_to_photo(idx, depth, show_thumb)`: для кандидата СКИПА
  `show_thumb=false` — миниатюра непроверенного файла не мелькает;
  `show_thumbnail` дополнительно не показывает битые.
- Открытие кликом/next/prev — `show_thumb=true` как раньше (миниатюра
  мгновенна для годных; битые там уже исключены навигацией).

**Итог:** fmt/clippy чисты, **70 тестов зелёных** (+4: edge-скип битых
вперёд/назад, cycle-заворот мимо битого, random-скип битых позиций,
весь список битый). Ожидание ручного теста: random на папке с кучей
битых показывает только годные случайные кадры, ничего не мелькает.

## Этап 4.4c-4. Предзагрузка соседей — по текущему порядку

**Симптом (после 4.4c-3).** «Открывает одну миниатюрку, потом прогружает
и меняет сам на иное фото — миниатюрки и большие фото в рассинхроне,
будто два разных рандома».

**Корень (найден по логу, строки 29014-29033).** Предзагрузка соседей
(механизм 4.3: пока смотришь кадр N, воркер заранее декодирует соседей)
считала соседей ЛИНЕЙНО — `index±1` по исходному списку. В random
«линейный сосед» — ЧУЖОЙ случайный кадр: его декод шёл в очередь, и при
гонках результат применялся к экрану, перебивая текущий кадр → «чёткое
само меняется на иное». Заказчик сформулировал ТЗ точно: «перемешанный
список — такой же список, просто в другом порядке, и ВСЁ листание идёт
по нему». Предзагрузка осталась линейной — вот и рассинхрон.

**Фикс — вся навигация (включая предзагрузку) по текущему порядку:**
- Чистая функция `preload_neighbors(index, count, radius, order, pos,
  broken)`: до 3 соседей в каждую сторону; в random соседи — фото с
  СОСЕДНИХ ПОЗИЦИЙ перемешанного списка (shuffle_pos±1..3), не линейные
  index±1; broken-индексы не предзагружаем (не тратим время воркера).
- `enqueue_preload` переведён на неё (было: тупо index±1).
- Двойная защита в воркере: результат применяется к экрану ТОЛЬКО если
  текущий `viewer-index` равен индексу задачи (сверка и поколения, и
  индекса) — «чёткое само меняется» исключено конструктивно.
- LRU-кэши 20 → 40: 3×2 соседей + текущие кадры должны помещаться.
- Число соседей — 3, не 30 (объяснено заказчику): один воркер декодирует
  по очереди, 30 забьют её и вернут затуп; быстрое листание и так тянут
  мгновенные миниатюры.

**Итог:** fmt/clippy чисты, **74 теста зелёных** (+4: линейные соседи,
край списка, random-соседи по перемешанному порядку, пропуск битых).
Ожидание ручного теста: миниатюра и чёткое — ОДНОГО кадра, ничего не
«меняется само», prev/next честные.

## Этап 4.4c-5. Инвариант экрана — кадр всегда равен viewer-index

**Симптом (после 4.4c-4).** «По началу работает, пролистал сотню фото —
опять глюкануло: миниатюрка одна, большое другое».

**Причина остаточной гонки.** Защита «показывать только свой кадр» стояла
в воркере (асинхронный путь) и сверяла индекс. Но в `request_load` есть
ещё ДВЕ СИНХРОННЫЕ ветки — кэш-хиты (UI-кэш готовых Image, RGBA-кэш):
они сверяли только ПОКОКОЛЕНИЕ, не индекс. Тонкая гонка: кэш-хиты разных
индексов в рамках одного поколения могли записать чёткое, не совпадающее
с последней миниатюрой. Редко (нужен кэш-хит в момент гонки) — потому
«по началу работает, глубже глюк».

**Фикс — ИНВАРИАНТ ЭКРАНА (требование заказчика: «что на миниатюре, то и
большое — строго-настрого»):** перед КАЖДЫМ `set_viewer_image` сверяем
текущий `viewer-index` с индексом задачи:
- воркер (async) — сверка была (4.4c-4);
- UI-кэш Image (sync) — сверка добавлена;
- RGBA-кэш (sync) — сверка добавлена;
- миниатюра — при отсутствии в модели слой ЧИСТИТСЯ (не «залипает» кадр
  прошлого перехода; уже было с 4.3i, проверено).

Теперь запись в слой возможна ТОЛЬКО для кадра, равного текущему
`viewer-index` — рассинхрон «миниатюра A / чёткое Z» исключён
конструктивно, во всех путях показа.

**Итог:** fmt/clippy чисты, **74 теста зелёных** (состав не менялся —
правка в ветках показа; логика покрыта тестами 4.4a–4.4c-4). Ожидание
ручного теста: deep-листание 100+ фото — миниатюра и чёткое строго
одного кадра.

## Этап 4.4c-6. Единый источник — миниатюра и чёткое по пути файла

**Симптом (после 4.4c-5).** «Он просто открывает одну миниатюрку, а
прогружает уже совсем иное фото — рассинхрон с первого же фото».

**Настоящий корень (не битые!).** Миниатюра и чёткое брались из ДВУХ
РАЗНЫХ списков по ОДНОМУ индексу:
- миниатюра: `thumbnails.row_data(index)` — модель галереи Slint;
- чёткое: `photos[index]` — `Arc<Mutex<Vec<Photo>>>` вьюера.

Это два независимых списка, и они РАСХОДЯТСЯ: при досскане (fingerprint,
4.7d) `photos` обновляется в фоне одним куском, а модель галереи —
другим `invoke_from_event_loop`; при батчах (4.4b) модель растёт
порциями. В момент расхождения один и тот же `index` указывает на
РАЗНЫЕ файлы → «миниатюра одна, чёткое другое». Все прошлые фиксы
(4.4c-2..5) чинили гонки записи, но не устраняли саму причину —
два источника.

**Фикс — ОДИН источник и ОДИН ключ (выбор заказчика).** Истина — путь
файла из `photos[index]` (его же грузит чёткое в `request_load`).
`show_thumbnail` ищет миниатюру в модели галереи по `source_path ==
path` (не по индексу!). Миниатюра и чёткое гарантированно одного файла;
если миниатюры по пути ещё нет (батч не дошёл) — слой чистится, чужой
кадр не показывается.

**Итог:** fmt/clippy чисты, **74 теста зелёных** (правка в показе;
поиск по пути — линейный, микросекунды на 10к, при необходимости
ускорим хэш-таблицей в 4.4d). Ожидание ручного теста: листание в
любом режиме — миниатюра и чёткое строго одного кадра.

## Этап 4.6a. Фаза 0 — логи [CONC]: видимость конкурентности

**Контекст.** Заказчик одобрил эксперименты по плану конкурентности
(`doc/dev_plans/04_concurrency_plan.md`), но методично: сначала
ВИДИМОСТЬ, потом потоки. Урок 4.3: гонки без видимости чинятся долго.

**Что сделано.** Единый префикс `[CONC]` в DEBUG-логах — грепается
одной командой, показывает полную судьбу каждого кадра:

- `worker: Photo idx=N gen=G depth=D skipped=S` — приём приоритетной
  задачи: индекс, поколение (идентификатор перехода), глубина скипа,
  сколько задач дренировано мимо (глубина очереди);
- `worker: Photo idx=N декод за X мс` — тайминг декода текущего кадра;
- `worker: Preload «путь» за X мс` — тайминг фоновой предзагрузки
  (видно, как сосед задерживал очередь);
- `worker: устарела gen=G` — задача отброшена (пользователь ушёл дальше);
- `show: thumb idx=N (по пути)` / `НЕТ в модели — слой очищен` —
  миниатюра найдена по пути или слой чист (не «залипает» чужой кадр);
- `put: ui-cache/rgba-cache/worker idx=N gen=G` — КАЖДАЯ запись чёткого
  в слой с источником и поколением.

По этим логам восстанавливается точная последовательность любого
глюка: какой кадр запросили → что показала миниатюра → что и откуда
записало чёткое → совпало ли с viewer-index. Без догадок.

**Технический нюанс.** `drain_to_last` теперь возвращает счётчик
пропущенных задач (глубина очереди). Отдельный task_id не вводили —
идентификатором служит generation (уникален на переход, KISS).

**Итог:** fmt/clippy чисты, **74 теста зелёных** (логи не меняют
логику). Фаза 0 готова — эксперименты фаз 1-2 пойдут с полной
видимостью. Откат — тег v0.2.0.

## Этап 4.6b. Фаза 1 — приоритет текущего кадра (два канала на одном потоке)

**Контекст.** Логи `[CONC]` (сессия 16:35:26–16:36:03, random-режим,
~10.6 тыс. фото) подтвердили корень тормоза «размытая миниатюра висит
~10 сек»: единственный воркер-поток брал задачи из ОДНОЙ FIFO-очереди,
и тяжёлый сосед-`Preload` вставал ПЕРЕД текущим кадром. Примеры из
лога: idx=411 ждал 2999 мс, пока декодился сосед 1536×2736; idx=9870
ждал 5491 мс из-за соседа 3840×2160. `drain_to_last` берёт последнюю
Photo-задачу, но НЕ прерывает уже идущий декод соседа. Инвариант
«кадр = viewer-index» при этом НЕ нарушался — рассинхрона в логе нет,
проблема чисто в порядке обслуживания очереди.

**Что сделано (Фаза 1 — минимальный риск, БЕЗ новых потоков).**
Канал воркера расщеплён на ДВА, поток по-прежнему один:

- `priority` — только `LoadTask::Photo` (текущий кадр). Сюда шлёт
  `request_load` (ветка «мимо кэша»);
- `bg` — только `LoadTask::Preload` (соседи). Сюда шлёт
  `enqueue_preload`;
- новая функция `recv_priority_aware(priority_rx, bg_rx, idle_poll)`:
  сначала `try_recv` из priority → если пусто, ОДНА задача из bg →
  если оба пусты, блокирующее `recv_timeout(100 мс)` на priority
  (холостого опроса нет, CPU не жжём). Между соседями priority
  проверяется снова — нажатие пользователя всегда побеждает фон;
- `ViewerCtx` хранит оба отправителя (`priority_tx`/`bg_tx`);
- `drain_to_last` работает по priority-каналу, как раньше.

**Почему безопасно.** Поток по-прежнему ОДИН — новых гонок не
появилось физически. Инвариант «кадр = viewer-index» (4.4c-5) не
тронут: обработчик `Photo` внутри воркера не изменился, все сверки
поколения и индекса на месте. `LoadTask` остался одним enum — оба
канала несут один тип (KISS).

**Итог:** fmt/clippy чисты, **74 теста зелёных** (логика навигации и
скипа не менялась — тесты их и покрывают). Критерий приёмки: при
листании чёткое приходит раньше соседей — по логу `Photo` декодируется
до `Preload`. Откат — тег v0.2.0.

**Приёмка (по свежему логу, сессия 18:02:39–18:04:05).** Фаза 1
подтверждена: очередь больше не блокирует кадр — воркер берёт Photo
сразу, соседи не мешают. Оставшийся тормоз — ДРУГОЙ, более
фундаментальный: скорость декода ОДНОГО тяжёлого файла. Пример:
idx=950, PNG 5760×6480 (~37 Мп) — downscale до ≤2560 занял **15.9 с**
чистого CPU на одном ядре (i5-1235U — энергоэффективный 15-ваттный
чип), очередь при этом была ПУСТА. Предпоследний кадр (3840×2160) —
6.3 с по той же причине. Вывод: Фаза 1 закрыла дисциплину очереди;
дальше ускорять нужно сам декод — это Фаза 2 (rayon, все ядра), с
настройкой-галкой «Ультра-скорость» (по умолчанию ВЫКЛ — бережёт
батарею ноутбука), по решению заказчика.
